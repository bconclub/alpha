# Alpha audit, September 6, 2026

## Verdict

The available history does not establish a deployable profitable strategy. Repeated strategy changes were followed by losses, and the present backtest does not simulate the present live strategy. Repair validation, accounting and operational controls before selecting a replacement. This audit changes no live settings and places no orders.

Confidence is high for code findings and reproduced database totals; strategy superiority and exchange-reconciled lifetime cash P&L remain unproven.

## Verified validation defects

Sources: `engine/scripts/backtest_v5.py`, `engine/alpha/live_trader.py`, `engine/alpha/strategy_v3.py`.

- Simulator omits live +25% take-profit and -26% margin loss cap. Earlier leverage ablation explanations claiming simulated loss-cap clipping were unsupported by this script.
- Simulator applies fractional fixed notional independently per pair. No integer contracts, exchange minimums, shared balance, three-position portfolio limit, margin reservation, daily-loss gate or balance kill gate.
- Aggregate drawdown iterates trades concatenated by pair, not a chronological portfolio. Reported `maxDD` is not actual portfolio drawdown.
- Sim ATR excludes the signal bar (`range(j-period, j)`), whereas live `_atr_rows(closed)` includes it. Refresh timing also differs: closed-bar simulation versus a 15-minute live ATR cache.
- Simulator stops fill exactly at stop price even on gaps. No slippage, funding, partial execution, API outage or live sampling model.
- Simulation uses 5-minute highs/lows to update extrema; live samples ticker prices. Trail paths can differ even with identical entry signals.
- Sim labels terminal marks as completed P&L and reports monthly results by entry timestamp. This is not the same as live realized P&L by close date.
- `--split` partitions trades by entry time; trades may close after a split boundary. It is not automatically a leakage-free walk-forward experiment.
- Claimed selection among 141 configurations using both windows' profitability contaminates the nominal holdout if that window helped select the winner. Stored commentary is not a substitute for immutable trial results and an untouched final test.

## Verified live/control weaknesses

- `_open` rounds up to one contract when fixed target notional is too small. BTC position margin became roughly $8 instead of intended $3. There is no per-order free-margin reservation/check in that method.
- Pair iteration preserves configured order, with BTC first in the default universe. It is not a ranked selection of the best simultaneous opportunities. This can create capital allocation bias.
- Signal key is consumed during evaluation before affordability/order success is known. It is in memory only: failed/blocked entries can be missed; restarts can expose the same candle again.
- Daily realized-loss counter initializes to zero on process creation. It is not restored from that day's closed trades in this class. Restarts weaken the daily gate; existing positions can also lose after new entries are gated.
- Visible entry/exit path uses bot-managed market exits, with no protective stop placement in that path. Ticker-fetch failure returns before stop management. Current exchange open-order protection was not independently reconciled.
- Fee accounting uses a flat 0.0005 per side. Another engine path documents 0.000590 including GST. This internal inconsistency requires reconciliation to actual fill commissions and funding, not blindly substituting a new constant.
- `confidence` is `90 + min(breakout_pct,1)*8`, capped at 98. It is a breakout score, not trained win probability. No model training/inference exists in the current signal path examined.
- Sitrep can print `none open` after failed account/position retrieval and can substitute zero for unavailable prices. Unknown state must not appear as verified flat or zero P&L.

## Required sequence

### 1. Establish trustworthy evidence

Reconcile fills, fees, funding and cash movements to the exchange. Preserve raw fills and deployment/configuration IDs per trade; separate manual, autonomous, paper and corrected legacy rows. Recover older history if still available. Report realized P&L and marked equity separately.

### 2. Repair research before optimizing

Build a chronological shared-account replay using the same signal/ATR/exit definitions as live. Include contract steps, free margin, fees/funding, target and loss cap, daily gates, restart semantics and conservative gap handling. Demonstrate parity on representative actual winners, losers, simultaneous signals, rejected orders and restart cases before accepting new performance numbers.

### 3. Resolve operational defects separately

Design durable signal/order identity, reconciliation after ambiguous order responses, persistent daily risk state, valid-price freshness checks and exchange-side protection with verified acknowledgement. Test these changes in paper/test environments. Monitoring must survive the desktop session and distinguish unavailable data from healthy state.

### 4. Run a small, preregistered strategy comparison

Compare baseline 2h breakout with and without TP25 first; compare BTC-enabled and BTC-disabled feasible sizing next. Only then consider breakout-and-retest as a new hypothesis. Historical retest paper lane was also negative, so this is not a newly discovered cure. Avoid combining many untested filters.

Evaluate unseen chronological periods, multiple regimes, fee/slippage stress, capacity-adjusted return, drawdown and uncertainty. At the current balance, contract minimums may make any reasonable account-risk budget infeasible. Skipping a trade is a valid outcome; raising leverage to force a fill is not evidence of improved expectancy.

## Corrections to earlier conversation

- No basis for calling the August market a guaranteed favorable regime or promising added funds would multiply profit proportionally.
- The existing simulator did not prove current live strategy profitable and did not model the quoted loss-cap leverage explanation.
- Positive runs of several trades were real recorded outcomes, not evidence of durable profitability.
- DB and network errors cannot be universally classified as benign when software exits depend on network access and records support reconciliation.
- Do not claim all data from inception has been recovered. This audit establishes the available retained history and its limits.

## Decision

Do not select or promote a replacement live strategy from these results. First deliver exchange reconciliation and a live-parity replay. Those are the actionable improvements supported by this audit. No live deployment, restart, trade, or risk-limit change was made.
